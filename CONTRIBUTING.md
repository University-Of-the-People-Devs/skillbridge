# Contributing to SkillBridge 🌍

Thank you for your interest in contributing to SkillBridge.

SkillBridge is an open-source project built collaboratively by students and developers from around the world. Every contribution matters, whether it is code, documentation, design, testing, research, or ideas.

Our goal is to maintain a professional development environment where contributors can learn, collaborate, and build real-world software engineering experience.

---

## 🌱 Who Can Contribute?

Everyone is welcome to contribute.

You can contribute as a:

* Frontend developer
* Backend developer
* Full-stack developer
* Mobile developer
* UI/UX designer
* AI/ML developer
* Database developer
* DevOps engineer
* Cybersecurity contributor
* QA/tester
* Technical writer
* Researcher
* Project manager

You do not need to be an expert to contribute.

Beginner-friendly issues will be clearly marked.

---

## 🔄 Contribution Workflow

All contributions should generally follow this process:

```text
Find an Issue
     ↓
Discuss / Claim the Issue
     ↓
Create a Branch
     ↓
Develop Your Changes
     ↓
Test Your Changes
     ↓
Commit Your Changes
     ↓
Open a Pull Request
     ↓
Code Review
     ↓
Address Feedback
     ↓
Approval
     ↓
Merge
```

---

## 1. Find an Issue

Before starting work, look through the project's GitHub Issues.

Look for labels such as:

* `good first issue`
* `beginner`
* `frontend`
* `backend`
* `documentation`
* `testing`
* `design`
* `help wanted`

If an issue is already assigned to another contributor, please choose another issue unless the maintainer asks you to collaborate.

---

## 2. Claim an Issue

Comment on the issue to indicate that you would like to work on it.

Example:

> I would like to work on this issue. I have experience with React and TypeScript.

Wait for confirmation from a maintainer before beginning significant work.

This helps prevent multiple contributors from unknowingly working on the same task.

---

## 3. Create a Branch

Do not work directly on the `main` branch.

Create a branch based on the type of work.

### Feature

```text
feature/short-description
```

Example:

```text
feature/student-profile
```

### Bug Fix

```text
fix/short-description
```

Example:

```text
fix/profile-validation
```

### Documentation

```text
docs/short-description
```

Example:

```text
docs/api-documentation
```

### Design

```text
design/short-description
```

Example:

```text
design/profile-dashboard
```

---

## 4. Keep Changes Focused

A pull request should normally solve one issue or accomplish one clearly defined task.

Avoid combining unrelated changes.

For example, do not combine:

* Authentication changes
* Dashboard redesign
* Database migration
* Documentation changes

into one large pull request unless they are directly related.

Smaller pull requests are easier to review, test, and maintain.

---

## 5. Write Clear Commits

Use clear and meaningful commit messages.

Examples:

```text
feat: add student profile creation
```

```text
fix: resolve profile validation error
```

```text
docs: update contribution guide
```

```text
test: add authentication tests
```

```text
refactor: simplify project matching logic
```

Avoid unclear messages such as:

```text
update
```

```text
changes
```

```text
final
```

---

## 6. Test Your Changes

Before opening a pull request:

* Make sure the application runs correctly.
* Test the functionality you changed.
* Check for obvious errors.
* Make sure existing functionality has not been unnecessarily broken.
* Follow the project's coding standards.

If tests are available, run them before submitting your pull request.

---

## 7. Open a Pull Request

When your work is ready, open a Pull Request against the appropriate development branch.

Your pull request should explain:

### What did you change?

Briefly describe the implementation.

### Why did you make the change?

Explain the problem or requirement being addressed.

### How was it tested?

Explain what you tested.

### Related Issue

Reference the relevant GitHub issue.

Example:

```text
Closes #24
```

---

## 8. Code Review

Every significant code contribution should be reviewed before merging.

Reviewers may request:

* Changes to the implementation
* Additional tests
* Better documentation
* Improved naming
* Security improvements
* Performance improvements
* UI/UX adjustments

Please treat code review as part of the learning and collaboration process.

---

## 9. Respect Other Contributors

SkillBridge is an international community.

Contributors may have different:

* Countries
* Time zones
* Experience levels
* Technical backgrounds
* Communication styles

Be respectful, constructive, and professional.

Critique the code or implementation, not the person.

---

## 🧑‍💻 Development Principles

We aim to build SkillBridge using professional engineering practices.

Contributors should prioritize:

* Clean and maintainable code
* Security
* Accessibility
* Performance
* Testing
* Documentation
* Scalability
* Reusability
* Good user experience

---

## 🚫 Do Not

Please do not:

* Push directly to `main`
* Submit code copied without understanding its license
* Commit passwords, API keys, or secrets
* Submit unrelated changes
* Intentionally introduce vulnerabilities
* Close another contributor's issue without authorization
* Submit pull requests solely for contribution statistics
* Harass or disrespect other contributors
