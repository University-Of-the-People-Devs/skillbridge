# SkillBridge Contributor Guide

Welcome to SkillBridge.

SkillBridge is a global open collaboration project designed to connect students and emerging developers from different parts of the world to build meaningful, real-world software projects together.

This project is being developed by contributors from the community. No single person is expected to build the entire platform.

Every contribution matters.

---

# 1. What Is SkillBridge?

SkillBridge connects people with skills to real-world projects where they can collaborate, gain practical experience, build professional relationships, and demonstrate what they can actually create.

The core idea is:

> **Connect. Collaborate. Build. Prove. Grow.**

SkillBridge aims to reduce the gap between learning and practical experience by giving students and emerging developers an opportunity to work together on real projects.

---

# 2. Why Contribute?

Contributing to SkillBridge gives you an opportunity to:

* Work on a real-world software project.
* Collaborate with developers from different countries.
* Practice professional Git and GitHub workflows.

You do not need to be an expert to contribute.

Contributors at different experience levels are welcome.

# 5. How Contributions Work

SkillBridge uses a collaborative GitHub workflow.

The general process is:

```text
Find an issue
      ↓
Understand the task
      ↓
Discuss or claim the issue
      ↓
Create a branch
      ↓
Implement the change
      ↓
Test your work
      ↓
Commit your changes
      ↓
Open a Pull Request
      ↓
Code review
      ↓
Changes if necessary
      ↓
Approval
      ↓
Merge
```

Contributors should avoid making large changes without first discussing the work when the change affects the overall architecture or multiple parts of the platform.

---

# 6. Finding Something to Work On

Start by checking the GitHub Issues section.

Look for issues that:

* Are not already assigned.
* Match your skills.
* Match your experience level.
* Have clear requirements.
* Are appropriate for your available time.

If you find something you want to work on, comment on the issue before beginning significant work.

For example:

> I would like to work on this issue. I have experience with React and TypeScript and can take this task.

Wait for the issue to be assigned or otherwise confirmed before starting substantial implementation.

---

# 7. Creating a Branch

Never develop directly on the `main` branch.

Create a branch based on the type of contribution.

### Feature

```text
feature/short-description
```

Example:

```text
feature/project-discovery-ui
```

### Bug Fix

```text
fix/short-description
```

Example:

```text
fix/mobile-navigation
```

### Documentation

```text
docs/short-description
```

Example:

```text
docs/api-guide
```

### Design

```text
design/short-description
```

Example:

```text
design/project-dashboard
```

---

# 8. Commit Messages

Use clear and consistent commit messages.

Recommended prefixes:

```text
feat:
fix:
docs:
test:
refactor:
style:
chore:
perf:
security:
```

Examples:

```text
feat: add project discovery filters

fix: resolve mobile navigation issue

docs: improve contributor guide

test: add project application tests

refactor: simplify project card component

style: improve dashboard spacing
```

Commit messages should describe what changed.

Avoid messages such as:

```text
update

changes

done

final

new code
```

---

# 9. Pull Requests

When your work is ready, open a Pull Request against the appropriate branch.

The Pull Request should:

* Explain what was changed.
* Explain why it was changed.
* Reference the relevant issue.
* Include screenshots for UI changes.
* Explain how the change was tested.
* Mention any limitations.
* Identify breaking changes if applicable.

Use the repository Pull Request template.

---

# 10. Keep Contributions Focused

A Pull Request should normally solve one clearly defined problem.

Avoid combining unrelated changes.

For example, do not create one Pull Request containing:

* A dashboard redesign.
* Database changes.
* Authentication changes.
* Documentation changes.
* An unrelated bug fix.

Instead, separate them into appropriate issues and Pull Requests.

Focused contributions are easier to review, test, and merge.

---

# 11. Working With Other Contributors

SkillBridge is a collaborative project.

You may work with contributors you have never met and who live in different countries.

Always:

* Communicate respectfully.
* Explain technical decisions.
* Ask questions when requirements are unclear.
* Help other contributors.
* Accept constructive feedback.
* Give constructive code reviews.
* Avoid unnecessary arguments.
* Respect different experience levels.
* Keep discussions focused on the project.

Different opinions are expected.

Professional collaboration matters more than winning an argument.

---

# 12. Code Reviews

Code review is part of the development process.

Reviewers may check:

* Functionality.
* Code quality.
* Security.
* Performance.
* Accessibility.
* Maintainability.
* Testing.
* Consistency with project architecture.
* User experience.

A request for changes is not a rejection of the contributor.

It is part of building a better product.

Contributors should respond to review comments professionally and update their Pull Request where appropriate.

---

# 13. Before Opening a Pull Request

Make sure you:

* Test your changes.
* Check for TypeScript errors.
* Check for console errors.
* Check responsive behavior.
* Review your own code.
* Remove unnecessary code.
* Remove debugging statements.
* Update documentation when necessary.
* Confirm that unrelated functionality still works.

For UI changes, provide screenshots or a demonstration when useful.

---

# 14. AI-Assisted Development

AI tools may be used to assist with development.

Examples include:

* Claude.
* ChatGPT.
* GitHub Copilot.
* Other coding assistants.

However, contributors remain responsible for the code they submit.

Do not blindly copy and submit AI-generated code.

Contributors should:

* Understand the generated code.
* Review it carefully.
* Test it.
* Check security implications.
* Check dependencies.
* Verify that it follows SkillBridge architecture.
* Ensure it solves the actual issue.

AI should accelerate collaboration, not replace engineering judgment.

---

# 15. Security

Security is everyone's responsibility.

Never commit:

* API keys.
* Passwords.
* Authentication tokens.
* Private keys.
* Database credentials.
* Environment files containing secrets.
* Personal confidential information.

Never intentionally introduce:

* Malware.
* Backdoors.
* Credential theft.
* Unauthorized access.
* Vulnerable dependencies.
* Data exposure.

If you discover a serious security vulnerability, do not publicly expose sensitive details in a normal issue.

Report it through the project's designated security reporting process.

---

# 16. Personal Data

SkillBridge is intended to become a global platform.

Contributors should treat user data carefully.

Do not collect, expose, or store personal information unless it is necessary for a legitimate product requirement.

Security and privacy should be considered whenever developing features involving:

* Profiles.
* Authentication.
* GitHub accounts.
* Applications.
* Messages.
* Contributions.
* Organizations.
* Opportunities.

---

# 17. Designing for a Global Community

SkillBridge is intended for users around the world.

Contributors should consider:

* Different countries.
* Different time zones.
* Different devices.
* Different internet speeds.
* Different levels of technical experience.
* Mobile-first usage.
* Accessibility.
* Internationalization.
* Different educational backgrounds.

Avoid designing features around assumptions that only apply to one country or region unless the feature specifically requires it.

---

# 18. Mobile-First Development

A significant portion of SkillBridge users may access the platform from mobile devices.

Interfaces should therefore work well on:

* Small phones.
* Large phones.
* Tablets.
* Laptops.
* Desktop computers.

Do not assume that users have high-end computers or large screens.

---

# 19. Open Source Principles

SkillBridge is built around open collaboration.

Contributors should:

* Share knowledge.
* Document important decisions.
* Help new contributors.
* Keep discussions constructive.
* Respect existing contributors.
* Make code understandable.
* Avoid unnecessary complexity.

The goal is not merely to write code.

The goal is to build something that a global community can maintain together.

---

# 20. Proposing Major Changes

If you want to introduce a major architectural or product change, do not immediately implement it.

First create or discuss an issue explaining:

* The problem.
* The proposed solution.
* Why it is necessary.
* Expected benefits.
* Potential risks.
* Alternatives considered.

Major changes should receive community discussion before implementation.

---

# 21. Learning Contributions

SkillBridge welcomes contributors who are still learning.

If you are new to a technology:

1. Read the relevant documentation.
2. Ask questions.
3. Start with a manageable issue.
4. Study existing code.
5. Make a small contribution.
6. Request feedback.
7. Improve your implementation.

Good first contributions may include:

* Documentation.
* UI improvements.
* Accessibility fixes.
* Tests.
* Small bug fixes.
* Minor frontend components.

Contributors are encouraged to grow into larger responsibilities over time.

# 23. What SkillBridge Expects From Contributors

We expect contributors to demonstrate:

### Responsibility

Take ownership of the work you agree to do.

### Communication

### Quality

Submit work that has been tested and reviewed.

### Respect

Treat all contributors professionally.

### Learning

### Collaboration

Work with others instead of working in isolation.

### Integrity

Do not claim work you did not perform.

---

# 24. If You Cannot Finish an Issue

Life, school, work, and other responsibilities can affect availability.

If you cannot continue with an assigned issue, simply communicate it.

For example:

> I am currently unable to continue with this issue due to other commitments. I would like to release it so another contributor can take over.

There is no penalty for being honest about your availability.

Clear communication helps the entire team.

# 26. The Bigger Goal

SkillBridge is more than a collection of code.

It is an experiment in global collaboration.

The goal is to bring together people who may never have had the opportunity to work together otherwise.

A student in one country should be able to collaborate with a developer in another country, build something meaningful, and have that work become evidence of their practical ability.

That is the value SkillBridge is trying to create.
